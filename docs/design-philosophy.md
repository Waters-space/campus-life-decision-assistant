# 设计理念

## 1. 从“信息查询”走向“行动决策”

学生面对的通常不是单一问题，而是一组互相影响的限制：现在几点、食堂是否还营业、快递点什么时候关门、哪间教室可用、地点之间要走多久。传统校园信息分散在公众号、网页、群通知和地图中，用户需要自己检索、核对并安排顺序。

本项目的核心不是让 AI 说得更多，而是把这些零散信息压缩为一条可执行建议：先识别需求，再调用必要的数据能力，最后说明“推荐什么、为什么、下一步怎么做”。

## 2. 六类能力，按需组合

系统把校园生活拆成餐饮、快递、空闲教室、二手教材、当前时间和路线规划六类能力。每一类能力都可以独立迭代；涉及多个事项时，由智能体选择相关 Skill 并综合结果，而不是把所有工作流每次都跑一遍。

这样设计有三个好处：

1. 单一问题只调用一个最相关能力，降低等待时间和成本。
2. 多事项问题可以组合多个能力，不受固定线性流程限制。
3. 某个知识库或外部接口异常时，不会拖垮全部功能。

## 3. 事实来自资料，模型负责组织

知识库、时间服务和地图 API 提供事实；大模型负责理解问题、选择工具、解释结果和组织语言。系统提示词明确禁止模型把常识猜测成校园事实。

例如，教室资料只能证明某间教室的基础信息和标注时段，不能证明现场一定有座位；二手教材资料可以提供发布信息，但不能保证库存仍在；路线只有在起终点均精确匹配后才输出距离与逐段导航。

## 4. 最小追问与可解释输出

用户已经给出的信息应尽量直接利用。只有缺少决定性条件时才追问，而且每次只问一个最容易回答的问题。输出先给结论，再给依据、限制和下一步，避免让用户阅读冗长推理过程。

## 5. 前端不是聊天框的复制品

用户端承担“理解应用、快速进入、获取校园信息”的职责：首屏卡片说明产品价值，场景入口帮助学生形成问题，新闻和常用网站提供非 AI 的确定性入口，深浅主题适配不同使用环境。智能体聊天页面作为独立服务打开，使内容门户与 AI 编排可以分别部署、升级和回滚。

## 6. 可迁移，而不是绑定一所学校

代码、提示词规则和工作流结构保持通用；学校名称、图片、网站链接、知识库与平台 UUID 都通过配置或内容管理替换。迁移到新校园时，主要工作应是核验数据与重建知识库，而不是重写整套前端。
